# 우리 가족 체크노트 (GitHub Pages + Google Sheets)

> 2026-11-12 구현 초안 v1.1.0. 프런트엔드 / Apps Script 서버 소스가 포함된 **배포용 프로젝트**입니다. 실제 서버 배포·실사용 검증은 별도 수행해야 합니다.

## 가족 공간

| 가족 코드 | 노출 이름 | 최초 프리셋 | 초기 상태 |
|---|---|---|---|
| `ew-he` | 은원 & 하은 | 출산가방·집안 준비물 76개 + 일정 14개 | 모두 미완료 |
| `ce-hy` | 채은 & 하영 | 출산가방·집안 준비물 76개 + 일정 14개 | 모두 미완료 |
| `hr-yw` | 하람 & 예원 | 24~36개월 미래 준비 로드맵 32개(할 일 22 + 물품 10) | 모두 미완료 |

> **중요:** 이 앱의 공개 파일에는 자녀 이름과 실제 출생일을 포함하지 않습니다. 최초 잠금 해제 후 `설정 → 아이 출생일 / 이름`에서 등록하면 암호화되어 가족 DB에 저장됩니다. 출생일을 입력하지 않으면 월령 기준 일정은 실제 날짜로 계산되지 않습니다. 출산 프리셋의 과거 제품 참고 가격은 2025년 원본 자료입니다. 현재 가격·실제 지출이 아니므로 예상 지출에 자동 합산하지 않습니다. 월령 로드맵 역시 실제 완료/접종 기록을 추정하지 않습니다.

### 하람 & 예원 프리셋 (기존 육아 기록과 역할 분리)

- **일회성 미래 일정 22개:** 4·5차 영유아 건강검진, 1·2차 구강검진, 접종 기록 확인, 어린이집 새 학기, 두 돌, 보육·지원금 확인, 카시트·안전 점검 및 분기별 지출 계획 등.
- **구매·교체 검토 10개:** 시즌 의류, 신발, 놀이 교구, 새 학기 준비물, 안전용품 등. 실제 구매 필요 여부와 금액은 직접 등록합니다.
- **반복 육아 기록 없음:** 수면 기록, 식사/양치, 매일 등원 준비, 발달 관찰 등은 기존 ‘유하 육아 도구 모음’에서 담당합니다.
- **날짜 관리:** 출생일을 로그인 후 설정에 입력하면 생후 N개월 기준 일정이 월 단위로 계산됩니다. 앱 목표 날짜는 예약을 위한 참고일로 법정 마감일이 아닙니다. 출산/구강 검진 및 지원금 시기와 조건은 해당 연도 확인이 필요합니다.
- **계정 보안:** 새 부부의 기록은 아이 이름·출생일·진행 상태·지출까지 암호화 후 전용 시트에 저장되며, GitHub 코드에 개인정보는 넣지 않습니다.
- **기존 v1 프리셋 사용 중인 기기:** 최초 등록 완료된 계정에서는 새 프리셋으로 자동 초기화하지 않습니다. 이미 입력한 기록 손실을 막기 위한 동작입니다. v1에서 실제 사용을 시작했다면 별도 데이터 이전을 결정해야 합니다.

## 저장 아키텍처

```
브라우저 (GitHub Pages)
  │ 가족 선택 → 최초 초대 코드 + 4자리 숫자 PIN (숫자 패드)
  │ PBKDF2-SHA256(310,000회, 임의 salt)로 64바이트 도출
  │ ├─ 앞의 32바이트: AES-256-GCM 암호화 키 (브라우저에만 보관)
  │ └─ 뒤의 32바이트: 인증 파생값 → SHA256 해시를 서버 검증값으로 등록
  │
  └─ HTMLService 내부 iframe과 postMessage (허용 출처 + 매 접속 nonce 검증)
         ↓
Google Apps Script 웹앱 [Bridge.html / Code.gs]
  │ 초대 코드 검증(첫 등록), 해시 검증(로그인/저장)
  │ LockService + 버전 비교 → 충돌 시 덮어쓰기 중지
  │
  └─ 전용 Google Sheet `APP_DB`
     가족 코드 / KDF salt / 인증 검증값 / revision / 업데이트 시각 / AES-GCM 암호문 조각
```

DB 소유자에게 저장되어 있는 것은 **암호문**입니다. 브라우저에서 비밀번호가 없으면 내용을 해독할 수 없도록 했습니다. 단, 4자리 PIN은 조합이 1만 개뿐이므로 암호문 유출 시 오프라인 대입 공격에 취약합니다. 이는 가족 사이의 간편 잠금을 위한 설계이며, 앱 코드를 배포·변경할 권한이 있는 운영자는 원리상 이후 접속 시 비밀번호를 수집하도록 코드를 변조할 수 있으므로 운영자조차 절대 접근할 수 없다는 식의 보장은 하지 않습니다. GitHub 계정 접근 보안(2단계 인증, 배포 변경 기록)이 중요합니다.

## 설치와 배포

### 1. Google Sheets 전용 DB

기존 자산관리 원본 시트를 **직접 연결하지 마세요.** 새로 생성한 별도 시트를 사용해야 합니다. 3개 가족의 데이터를 하나의 DB 탭에 암호문으로 저장합니다. **가족에게 Google Sheets 직접 공유 권한을 주지 마세요.**

### 2. Google Apps Script 백엔드

1. 전용 Sheet에서 `확장 프로그램` → `Apps Script`로 들어갑니다.
2. `apps-script/Code.gs`를 스크립트 편집기에 전부 붙여넣습니다.
3. 좌측 `+` → `HTML` 파일을 `Bridge`라는 이름으로 만들고 `apps-script/Bridge.html`을 붙여넣습니다.
4. Apps Script 상단 함수 목록에서 **`generateEnrollmentCodes`를 한 번 실행**하고 권한을 승인합니다. **이 단계에서 바인딩된 전용 Google Sheets ID와 허용된 GitHub Pages 출처가 자동으로 스크립트 속성에 설정됩니다. 별도 속성 입력은 필요 없습니다.** 반드시 `APP_DB` 탭이 있는 전용 DB 시트에서 `확장 프로그램 → Apps Script`로 연 프로젝트에서 실행하세요. 실행 로그에는 `ew-he`, `ce-hy`, `hr-yw`별 **별도 1회용 초대 코드**가 표시됩니다. 안전한 경로로 각 부부에 전달하세요. 서버에는 코드 원문이 아닌 SHA-256 해시만 저장하고 등록이 끝나면 삭제합니다.
5. `배포` → `새 배포` → **웹 앱**으로 배포합니다. `실행 사용자`는 **나**, `액세스 권한`은 **모든 사용자**를 선택합니다. 앱 자체에서 초대 코드·파생 인증값을 검증하므로 Google 계정 로그인이 없어도 접속할 수 있습니다.
6. `https://script.google.com/macros/s/.../exec` 모양의 배포 주소를 복사합니다. Apps Script 코드를 수정한 뒤에는 **새 버전으로 배포 업데이트**해야 적용됩니다.

> **보안:** 웹앱은 공개 엔드포인트이므로 부부 전용 초대 코드와 4자리 숫자 PIN를 설정해야 합니다. 4자리 PIN은 강한 공격에 대한 보안 수단이 아니므로 특히 GitHub·Google 계정 2단계 인증이 중요합니다. 코드 재사용을 막았으나 로그인 요청에 대한 IP 단위 강력한 속도 제한은 이 구현에 없습니다. 공개 대규모 서비스로 확장하려면 추가적인 서버 측 레이트리밋·보안 점검이 필요합니다.

### 3. GitHub Pages

1. GitHub에 별도의 저장소를 새로 만듭니다. 추천 이름: `FAMILY-BABY-CHECK`.
2. 이 압축 파일의 **프로젝트 내부 파일과 폴더를 저장소 최상단**에 업로드합니다. `apps-script` 소스와 README도 버전 관리하세요. **초대 코드, 비밀번호, 시트 DB ID, 다운로드한 가족 데이터는 GitHub에 올리지 마세요.**
3. `config.js`의 `backendUrl`에 2번에서 복사한 Apps Script `/exec` URL을 붙여넣고 커밋합니다. 이 주소는 공용 접근 URL이므로 비밀키가 아닙니다.
4. GitHub `Settings` → `Pages` → `Build and deployment`에서 `Deploy from a branch`, `main` / `(root)`로 게시합니다.
5. 예상 기본 주소는 `https://<GitHub ID>.github.io/<Repository Name>/` 형태입니다. `APP_ORIGINS`는 **도메인 origin**이므로 경로 `<Repository Name>`은 포함하지 않습니다.
6. 배포된 사이트에서 먼저 **하람 & 예원** 계정으로 초대 코드 + 비밀번호를 등록하고, 두 번째 기기에서 동일 비밀번호로 로그인해 동기화를 검증합니다. 그다음 두 가족의 첫 등록을 진행합니다.

### 4. 안전 검증 시나리오

- 세 부부가 각각 초대 코드로 **최초 비밀번호를 별도 설정**할 수 있는지 확인
- 같은 부부 2개 기기에서 입력한 물품명·금액·일정이 **암호화 동기화**되는지 확인
- 다른 부부 공간에서 입력한 내용이 **섞이지 않는지** 확인
- 비밀번호가 틀린 경우 복호화/로그인 실패하는지 확인
- 동시에 같은 항목 수정 시 한쪽의 저장이 `CONFLICT`로 중단되고 **강제 덮어쓰기를 자동으로 수행하지 않는지** 확인
- 네트워크 장애 시 기기에 암호화 상태로 보관되고 로그인 후 복원 가능한지 확인
- `APP_DB`에서 암호문이 아닌 **제품/이름/메모가 평문으로 들어가지 않는지** 확인
- 모바일에서 카드, 반복 체크, 탭 추가, 장기 일정, CSV/ICS, 암호화 백업 복원 확인

## 사용 및 한계

- 홈에서 준비 진행률·실제 지출·향후 예상 지출·14일 내 일정을 확인할 수 있습니다.
- 항목 수정에서 `가족에게 받기`, `직접 구매`, `집에 있음`, `중고`, `대여`, 제품명, 준 사람, 가격, 수량을 정합니다.
- `완료`는 준비 완료를 의미합니다. 가족에게 받기로 예정된 물품이라도 **실제 수령 전이라면 미완료로 두세요.**
- 하람·예원 가족의 기본 프리셋에는 반복 루틴을 넣지 않았습니다. 다른 가족이 직접 반복 항목을 추가하는 것은 가능하며, 반복 체크의 과거 일자별 히스토리는 별도로 보관하지 않습니다.
- 날짜·검진 예약 목표일은 편집 가능하며, 정부·보건 서비스의 법정 기간으로 자동 보장되는 것이 아닙니다.
- 앱 내 일정 배너는 접속 시 표시됩니다. **앱 자체가 백그라운드 알림을 발송하지 않습니다.** `.ics`로 휴대폰 캘린더에 가져오면 알림을 사용할 수 있습니다.
- `제품 참고`의 `추천 요청 복사`는 AI 호출을 자동 실행하지 않습니다. 새로 추천받은 내용을 GitHub의 `recommendations.js`에 반영하면 업데이트됩니다.
- `config.js`에 URL이 없으면 **로컬 미리보기 모드**입니다. 이 경우 저장은 그 브라우저에만 이루어지며, 서버 설정 후 로컬 데이터가 자동 이전되지는 않습니다.
- 비밀번호 분실 시 암호문 복호화가 불가능합니다. `암호화 백업`과 비밀번호를 **각각 안전하게** 보관하세요. 암호화 백업 불러오기는 같은 가족·같은 키로 등록된 공간에서만 허용합니다.
- Google Sheets는 고성능 동시 편집 DB가 아니며 한 가족당 한 덩어리 데이터를 저장합니다. 동시 수정 시 현재는 자동 병합 대신 충돌 해결을 요청합니다.

## 파일

| `index.html` / `style.css` | 모바일 카드형 UI · 부부 선택 · 동기화 상태 |
| `app.js` | 클라이언트 암호화·복호화·체크리스트·비용·일정·로컬 캐시 |

| `recommendations.js` | 공개된 추천 참고·선택 기준을 담은 업데이트 가능 목록 |

## 개인정보와 GitHub

공개 GitHub 저장소에 올라가는 것은 **코드와 공개 프리셋**이어야 합니다. 프리셋은 2025년 자료에서 이름·지원자·실제 지출·구매완료 등을 뺀 범용 항목으로 만들었습니다. 실제 가족 입력 데이터는 `APP_DB`의 암호문만 저장합니다. 앱 운영자의 권한으로 코드가 바뀔 위험을 줄이려면 보호 브랜치 및 2FA를 권장합니다.

## 소스 자체 검사

Node.js가 설치된 환경에서는 `node tests/check-presets.cjs`로 출산용 90개, 육아 로드맵 32개, 반복 기본값 제거, 월령 날짜 및 비용 계산을 검사할 수 있습니다. 이 검사는 Google Apps Script의 실배포 연결·모바일 브라우저 렌더링을 대신하지 않습니다.
